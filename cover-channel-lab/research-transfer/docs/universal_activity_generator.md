# Как добавлять свою активность в офисный фон

Генератор активности и смешивание — два отдельных шага. Генератор выполняет
нужное действие и записывает пакеты; общий конвейер переносит наблюдаемый обмен
в сохранённый фон, рассчитывает признаки и связывает их с разметкой.

Текущий общий вход — два изолированных Ethernet PCAP с TCP/UDP и файлы
подтверждения прикладного обмена. Генератор может быть написан на любом языке;
ему не нужны внутренние ID Cover Channels. Исследовательскую модель можно
обучать с явным ограничением области оценки. Для production нужны отдельная
проверка сигнала и подтверждение переноса в офис.

## 0. Среда, в которой снимается сценарий

Активность (что и когда отправляет приложение) вы не подгоняете. Но сенсор видит
ещё и путь: размер сегмента, TCP-опции клиента, задержку. Признаки сессии
считаются по самой сессии, поэтому подмешивание в фон не делает её естественнее:
естественность определяется средой, в которой она снята.

Параметры среды `office_path_v1` измерены по сохранённым офисным захватам, а не
по результатам модели (измерения и оговорки — `office_path_profile_2026-10-05.md`):

| Параметр | Значение | Откуда |
|---|---|---|
| MTU клиентского интерфейса | 1290 (клиент объявляет MSS 1250) | 100% клиентских SYN в интернет, 22 и 23.09 |
| TCP timestamps у клиента | включены в ~68% пар | 62,7% (22.09) и 85,6% (23.09) |
| RTT пути | 20 точек эмпирического распределения офиса | 132 207 сессий с измеренным RTT |

Встроенный генератор Cover Channels применяет их сам: `prepare_research_registry`
записывает параметры в каждый профиль, а `environment.apply` ставит MTU на обоих
концах клиентского veth и читает значения обратно. Для **стороннего** генератора
настройте то же самое у себя (клиентский интерфейс с MTU 1290) и объявите в
`activity.json`:

```json
"path_profile": "office_path_v1"
```

Тогда адаптер проверит по самому захвату, что в SYN клиента действительно MSS 1250,
а кадры не длиннее 1304 байт, и **откажется** принимать пару, если это не так.
Без поля `path_profile` пара принимается, но в каталоге остаётся
`path_conformance: not_declared`, а не «проверено». Ту же проверку можно запустить
отдельно:

```bash
PYTHONPATH=workspace/ops/remote python3 -m office_injection.path_conformance \
  --pcap scenario.pcap --client-ip 10.20.0.11 --timestamps on
```

Не воспроизводится и записано как известное ограничение: порядок TCP-опций
(Windows, Apple, Android), масштаб окна и TLS-стек клиента. Не подбирайте эти
значения до нужного AUC.

## 1. Запишите сценарий и обычный контроль

Например, подозрительный периодический DNS-обмен и обычные DNS-запросы.
Используйте одинаковое окружение и клиентский стек для обеих веток. Сохраняйте
реальную длительность и интервалы: не ускоряйте beacon ради учебного корпуса.

В каждый PCAP должна попасть только активность одной ветки, без постороннего
трафика. Для каждого TCP-потока нужен первый SYN от указанного клиента; для UDP
первый пакет тоже должен идти от клиента. Захват должен включать целые кадры,
иметь монотонные временные метки и ненулевую длительность. Адаптер не отрезает
неудобные пакеты и не превращает ICMP/фрагменты в TCP/UDP.

Если PCAP содержит смешанный фон, разные роли соединений или разные клиенты,
нужен отдельный адаптер точной принадлежности пакетов. Успех процесса и имя
файла не доказывают, что техника была выполнена. Сохраните журналы клиента и
сервера или receipt фактически выполненной операции. Общий адаптер проверяет
байты этих evidence-файлов, но не интерпретирует их смысл. Метка активности
здесь остаётся заявлением оператора, поддержанным сохранёнными подтверждениями.

## 2. Создайте activity.json

Все пути вычисляются относительно `activity.json`. SHA256 должны быть
фактическими хешами сохранённых файлов. Ниже пример структуры, не готовые хеши:

```json
{
  "activity_id": "custom_dns",
  "pair_id": "day1_pair001",
  "capture_environment": "isolated",
  "dataset_role": "scenario_and_matched_control",
  "arms": {
    "scenario": {
      "pcap": "scenario.pcap",
      "sha256": "SHA256_SCENARIO_PCAP",
      "source_ip": "10.20.0.11",
      "description": "Периодический DNS-обмен с выбранной механикой",
      "evidence": [{"path": "scenario_receipt.json", "sha256": "SHA256_SCENARIO_RECEIPT"}]
    },
    "control": {
      "pcap": "control.pcap",
      "sha256": "SHA256_CONTROL_PCAP",
      "source_ip": "10.20.0.11",
      "description": "Обычные DNS-запросы тем же клиентом",
      "evidence": [{"path": "control_receipt.json", "sha256": "SHA256_CONTROL_RECEIPT"}]
    }
  }
}
```

Хеши можно получить локально:

```bash
shasum -a 256 scenario.pcap control.pcap scenario_receipt.json control_receipt.json
```

Для легитимной активности, похожей на подозрительную, используйте роль
`hard_negative`: обе ветки получат нулевую метку. Не выдавайте легитимный
LOTS/privacy-сценарий за позитив.

```bash
PYTHONPATH=workspace/ops/remote python3 -m office_injection.activity \
  --spec activity.json --out prepared/custom_dns_day1
```

Адаптер сохраняет копии PCAP, receipts, пакетные observations и `catalog.json`.
Хеши копий проверяются повторно. Существующий каталог не перезаписывается.
Интервалы и байты исходных кадров не меняются. Обе ветки имеют общий предок,
вычисленный из хешей захватов: смена `pair_id` не делает копию пары независимой.
Дата исходного захвата сохраняется для группировки train/validation/test.

`training_eligible` и `timing_training_eligible` остаются false. Наличие PCAP
и подтверждений не доказывает естественность или наблюдаемость нужного сигнала.

## 3. Добавьте пару к уже сохранённому фону

В `office_inputs.json` перечислите доступные на этой машине `.pkts` файлы.
Каждому нужен соседний `.pay`. Эта команда не собирает трафик и не обращается
к сенсору. На исследовательском процессоре используйте Python с pandas/PyArrow.
Для стандартной структуры репозитория:

```bash
PYTHONPATH=workspace/ops/remote .venv/bin/python -m office_injection \
  --catalog prepared/custom_dns_day1/catalog.json \
  --office-inputs office_inputs.json \
  --out-dir runs/custom_dns_day1 --run-id custom_dns_day1 --repeats 2
```

В установленной автономной копии на `.18` пакет может лежать непосредственно
в текущем каталоге: тогда используйте `PYTHONPATH=.` и её интерпретатор.

`--repeats 2` означает одну пару, две ветки. При большем количестве повторов
счётчик должен быть чётным. Общий бюджет пары — 1% пакетов выбранного интервала.
Если пара не помещается по длительности или нагрузке, запуск отклоняется;
исходные временные интервалы не сжимаются для размещения. Для долгой активности
берите достаточно длинный сохранённый фон и подходящие границы batch.

Этот простой путь добавляет отдельные синтетические сессии. Он не внедряет
активность в поведение физического офисного хоста. Полный Cover Channels путь
`complete.execute_complete` создаёт clean/scenario/control и общую карту
логических хостов, а `campaign_features` считает окна по времени пакетов.
У этого пути остаются собственные обязательные registry/evidence контракты;
новый generic-каталог нельзя выдать за полное Cover Channels покрытие.

## 4. Проверьте разметку и признаки

| Часть | Ответ модели | Смысл |
|---|---|---|
| Сценарий | `label_binary=1` | Добавленная активность выбранной техники |
| Парный контроль | `label_binary=0` | Обычный обмен для сравнения |
| Hard negative | `label_binary=0` | Легитимная похожая активность |
| Офисный фон | NULL | Не проверен как безопасный |

Разметка привязана к наблюдаемым пакетам и распространяется на сессию.
`y_presumed` не заменяет ground truth. X храните отдельно от меток, ID, адресов,
портов, provenance и receipts. Сырой payload тоже не является меткой.

Для байтов различайте три величины:

- **Байты кадра:** включают сетевые заголовки; `total_bytes` не следует называть
  пользовательскими байтами без проверки определения признака.
- **TCP/UDP payload:** не включает заголовки транспорта; у TLS включает
  шифротекст, служебные записи и накладные расходы TLS.
- **Прикладные пользовательские байты:** требуют парсинга конкретного протокола
  и, для шифрованного содержимого, доступа к расшифровке. Размер исходного
  прикладного сообщения известен генератору, но не обязательно сенсору.

Генератор не должен подставлять своё знание plaintext в X пассивного сенсора.

## 5. Когда можно обучать

Для согласованного исследовательского среза 04.10 добавлен отдельный путь:

```bash
PYTHONPATH=workspace/ops/remote .venv/bin/python -m office_injection.research_training \
  --run <validated_complete_run> --out <new_research_directory>
```

Он сохраняет все размеченные сегменты много-сессионных кампаний, X и метки
отдельно. Целый профиль с обеими ролями и всеми повторными размещениями
остаётся в одной части train/validation/test. Признаки, модель и кластеризация
подбираются только на train. Офис не получает автоматически нулевые метки;
он используется отдельно для диагностики происхождения и совместных кластеров
без целевой метки. Fit совместных кластеров использует train-профили и офисный
референсный день; другой офисный день остаётся holdout. Полный X и X после
маргинального train-отбора сохраняются раздельно.

`research_training_ready=True` означает технически проверенный экспорт для
исследования. `production_training_ready` остаётся false. Деление профилей
внутри одного исходного дня не заменяет независимые позитивы офисного сенсора.
Производственный evaluator и его ограничения ниже остаются отдельными.

Для каждой техники сначала задайте ожидаемый наблюдаемый эффект. Затем отдельно
измерьте сценарий против контроля и контроль против офиса. Второе сравнение
показывает, может ли модель узнавать стенд вместо активности. Нужны различные
клиенты и серверы, независимые дни и позитивы, видимые офисному сенсору.
Все производные одной кампании/исходного дня должны оставаться в одной группе.
Отбор признаков делайте на train, подтверждение — на независимом holdout.
Совпадать должны и train/serve схема, и момент доступности признаков.

В текущей полной ревизии 02.10.2026: 63 из 89 признаков заметно различают
происхождение, одна независимая группа, парная session-оценка требует агрегации.
`full_review.evaluate_offline` сейчас намеренно не выполняет полную независимую
оценку при появлении >=3 групп: выбрасывает ошибку с требованием frozen full
evaluation. Это незавершённая часть универсального учебного процесса, а не
доказательство, что дальнейшее добавление дней автоматически разрешит обучение.

Нельзя гарантировать, что любая активность имеет отличимый сетевой сигнал.
Скрытое значение внутри одинакового TLS-обмена может быть недоступно выбранным
признакам. Сохраняйте честный статус `no_signal_detected` или `insufficient_data`,
когда измерение этого требует.

Публикация Bronze/Jupyter/GitHub остаётся на HOLD. Эти команды пишут только
локальные исследовательские артефакты. На `.136` и `enp0s3` они не работают.

## Проверенный пример обычной активности (6 октября 2026)

`framework_runtime/benign_web/capture.py` выполняет ограниченные HTTPS download,
upload и polling реальными Chrome/curl/Python. Рецепты и подтверждения создаются
отдельно от универсального импорта; `demo/run_web_supplement.py` формирует
`activity.json` с ролью `hard_negative`, проверяет путь и сохраняет обе ветки
как легитимные. По такой же границе можно подключать другие сетевые MITRE-сценарии:
меняется генератор и доказательство активности, общий перенос остаётся тем же.

Расширение обычных клиентов не прошло естественность: origin AUC ≈1 и 77 пакетов
с превышением эмпирической ёмкости временной модели. Подробности и статус —
[ordinary_web_revision_2026-10-06.md](ordinary_web_revision_2026-10-06.md).
После размещения проверяйте фактическую суммарную ёмкость по `placed.pkts` и
офисным строкам, включая неизменённые fallback-пакеты. Ошибка или отсутствующее
подтверждение не должны превращаться в статус «проверено». Для переносимости
нужны независимые офисные позитивы и сопоставимые легитимные контроли. Общий
адаптер сохраняет воспроизводимость; он не гарантирует сходство среды сам по себе.

## Следующая ревизия наблюдения и публичные ответы (6 октября 2026)

В `office-stamps-v4` устранены измеренные совпадения fallback-меток с заполненной
пачкой: дополнительный микросекундный шаг допускается только в пределах 500 мкс,
границы размещения и следующего пакета. Неизменные исходные группы времени не
разделяются. Общая ёмкость учитывает все кампании, исходные и дополнительные метки.
`pipeline.branch` сохраняет аудит и вызывает `require_complete()` до features:
неразрешённое переполнение означает отказ, а не успешную валидацию.

`framework_runtime/benign_web/public_capture.py` добавляет реальные публичные
HTTPS-ответы Chrome/curl. При доступе через прокси это явно отражается в evidence:
логическое отображение адреса не подтверждает физическую эквивалентность пути.
Браузерный валидатор проверяет целевой HTTP/2 stream, а не произвольный статус 200.
Сырые захваты неизменны. Общий `capture_order.canonicalize` может создать отдельную
копию с устойчивым порядком по исходным меткам, только если регрессия не превышает
10 мкс и порядок внутри каждого транспортного направления остаётся прежним.
Пакетные байты и сами метки проверяются точно; перестановки и оба SHA сохраняются.
Для других генераторов такая нормализация также требует этих условий.
